You have findAndCount. Why not find plus a separate count call? performance reason is that we do one operation instead of 2 functional reason is that its less code
edit:
Functional (correctness): both queries use the same where clause, so pagination math is always consistent. If you call find and count separately, you have to remember to pass the identical where twice. Forget one field, and total says 47 but the item pages only cover 30. findAndCount makes this class of bug structurally impossible.
Performance (marginal): both queries run in one transaction with the same snapshot, so you can't have a race where find sees 20 items but count (run 5ms later) sees 19 because someone deleted a post in between. On a busy forum, this matters for "Page 1 of 47" rendering.

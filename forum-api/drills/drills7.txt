Drill 3. Explain what a salt does in password hashing, and why two users with the same password have different passwordHash values in the database.
salt is some random bits put into password before hashing so single password can have multiple hashed
edit:
 a salt is unique per user, so even if 100 users all use password123, each one hashes to a different value. This defeats rainbow tables — precomputed lookup tables of hash('password123') → 'password123'. Without salts, an attacker who steals the DB can look up common passwords instantly. With salts, they'd have to brute-force each user individually.

Drill 7. Two requests hit /auth/register at the same time with the same email. What can happen without a DB-level unique constraint, and what happens with one?
without it there will be 2 same users with it 409 Conflict
edit:
Without the constraint: both requests pass the if (existing) pre-check (because the row isn't inserted yet in either transaction), then both INSERT successfully. You end up with two users with the same email. Data corruption.
With the constraint: one INSERT succeeds, the other throws SQLITE_CONSTRAINT. Your try/catch translates it to 409 Conflict. The race is resolved at the DB level — the pre-check is best-effort, the constraint is the actual guarantee.

edit:
passwordHash should never leave the users table. The only place it's allowed to exist is inside AuthService.login, where it's compared to the submitted password, and immediately discarded. It is not a field on "the user" from the client's perspective — it's an internal secret.
